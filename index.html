Case study 01

A single posting page with 16 states, resolved by priority

Role
Primary designer: plan, research, prototype
Team
Supervisor set requirements and reviewed; engineering ports it
Timeline
Oct 8 to 14, 2026, two iterations
State
Prototype, in review
Tools
Figma · React + TypeScript · Claude Code

Problem

The old page buried the application steps in the description and had no answer for what happens after you apply, or when a job closes, pauses or changes. The reader is often 16, on a phone, in a short window.

Result

The longest test posting went from about seven phone screens to about four. Pay is the largest thing on the page, every fact is stated once, and when there is nothing to do the sticky bar and checklist go away. No usage numbers yet; it is a prototype.

What I did, and the phone and desktop views
  • Wrote the plan: six principles, a field-by-field display rule table, a state table where the first true row wins.
  • Built a self-contained HTML prototype on the product's tokens, with five test postings and every state switchable.
  • Ran seven independent reviews of iteration one, one lens each, and merged them into one change list.
  • Kept applicant copy free of system nouns; empty sections hide, but pay says "Pay not listed".
  • Made print a real deliverable, since counselors print postings.

The reviews and the prototype scaffolding were AI-assisted; the plan, the state model and every design call are mine.

What I'd change: run it with a few real students. Every review so far was an expert or an AI lens, not a 16-year-old.

Case study 02

One task component, three surfaces

Role
Owned the UX and interaction design: cards, chips, filtering, states, full-page views
Team
Size not recorded; engineering owns the production build
Timeline
2025 to 2026
State
Approved prototype; task card and notification panel in design review, Oct 2026
Tools
Figma · HTML prototypes on the product's component CSS

Problem

Tasks are generated by the system, in five kinds, and reach a supervisor through the dashboard, a side panel and a full page. The same task has to read the same way on all three, with overdue work first.

Result

Approved, and now the reference for app chrome and card style on later pages. Rebuilt on the real component CSS, it matched the real components' markup state for state. Not in production yet, so not measured.

What I did
  • Defined one task anatomy: status chip, due date with lateness, title, apprentice, a "why this task" line, one primary action.
  • Dashboard shows three to five curated tasks with overdue pinned first; the full page is a queue with search, sort, filters and groups.
  • Each task opens a side panel with two actions; status chips stack in a fixed order so the same situation always looks the same.
  • Notifications as a bell-triggered panel in four categories, not an inbox. Progress bars deferred to a later version.
  • Status is never color alone: every chip has a word and overdue adds a date.

What I'd change: test snooze and undo with supervisors. The pattern has only been reviewed internally.

Case study 03

A swap-not-delete flow where the hours update live

Role
Designed course editing and replacement end to end: cards, hierarchy, filtering, recommended replacements, the swap flow
Team
Size not recorded
Timeline
2026
State
Interactive wireframe, version 5
Tools
Figma · HTML wireframe on the product's tokens

Problem

Every apprenticeship carries required classroom hours. Replacing a course must keep the level's hours, leave locked courses alone, and stay invisible to the apprentice until the plan is published.

Result

Locked courses stay visible with their reason, the replacement list is pre-filtered to what fits, and nothing changes until Confirm. Wireframe stage, so not yet measured.

What I did, and the edit panel
  • Course editing lives inside the training plan's edit mode, as a side panel scoped to one level.
  • Course card: provider, hours, format, included or free, competencies covered, and a lock state with its reason.
  • Swap is a replace: pick the course, choose from "Courses you can use instead", recommended first.
  • Hours math stays on screen; Cancel swap returns to the list with no side effects.

What I'd change: run the hour math against a real catalog. The wireframe uses five sample courses.

Case study 04

Keeping the design system and the code the same thing

Role
Translate the Figma design system into front-end components and keep design and code consistent
Team
Size not recorded; a brand approver signs off on brand decisions
Timeline
2026, ongoing
State
First token version implemented in the dev environment and Storybook
Tools
Figma · Storybook and Code Connect · CSS custom properties · React

Problem

Prototypes drift: a mockup with a hand-picked blue looks right in review, then looks different on the real components. A UI library in Unity or Unreal has the same problem: one source of truth, or two versions of the design.

Result

Components reference semantic tokens only, so a theme change touches one layer. Prototypes are rebuilt on the real component CSS with a check that fails on any raw hex, so "matches the product" is verified rather than claimed.

What I did, and a token excerpt
  • Two-layer tokens, primitives to semantics, exported to Figma and to CSS custom properties.
  • Guideline floors engineers use: measured contrast pairings, 14px functional text, 16px inputs, focus rings as outlines.
  • Icons linked between Figma and Storybook with Code Connect.
/* Tier 1: primitives. Private; only the semantic tier references them. */
--p-color-neutral-0: #FFFFFF;
--p-color-neutral-500: #64748B;
--p-color-navy-800: #0A2E52;

/* Tier 2: semantic. The only tier components use. */
--bg-surface: var(--p-color-neutral-0);
--bg-inverse-neutral: var(--p-color-neutral-900);

/* A component never sees a hex. */
.panel-header {
  background: var(--bg-surface);
  border-bottom: var(--border-width-1) solid var(--border-default);
}

Abridged from the generated token block in one of the prototypes above.

What I'd change: run the alignment check in CI instead of by hand.
